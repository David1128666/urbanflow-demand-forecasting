# UrbanFlow 通俗讲解文档

> **English summary:** This is a non-technical explanation of the problem,
> business value, prediction workflow, dashboard, and how to present the
> project in a portfolio or interview.
>
> **中文摘要：** 本文用通俗语言解释项目问题、业务价值、预测流程、页面用途，
> 以及如何在作品集或面试中介绍项目。

## 1. 一句话介绍

UrbanFlow 是一个“城市需求天气预报”系统：它根据过去的需求、天气和日期信息，预测未来 24 小时哪些地点可能出现需求高峰，并告诉运营人员应该优先关注哪里。

当前 MVP 先使用虚拟数据演示完整功能，不依赖真实城市数据。Flume、MLflow、PatchTST、概率区间和高级监控属于后期增强。

## 2. 为什么需要这个项目

最终项目可以面向一个有数百个共享单车停放点的真实城市。当前 MVP 先用 20 个虚拟站点验证功能。

早高峰时，有些地铁站附近的单车很快被骑走，车辆不够；另一些地方的车辆却一直停着。运营人员如果只看当前数据，问题是：

- 当系统发现某站没车时，用户已经受到影响。
- 当前有车不代表 30 分钟后仍然有车。
- 雨天、节假日和大型活动会突然改变需求。
- 人力有限，不可能同时给所有站点补车。

如果系统能提前 1 到 24 小时告诉运营人员：

> 明天早上 8 点，A 区三个站点需求可能明显高于平时，其中两个站点预测结果的不确定性较低，建议优先调度。

运营人员就能提前安排，而不是事后补救。

## 3. 用天气预报来理解

时间序列预测很像天气预报。

普通天气预报会告诉你：

- 明天几点可能下雨。
- 降水量大概是多少。
- 这个判断有多确定。

UrbanFlow 当前 MVP 告诉你：

- 未来哪个时间点需求高。
- 需求大概是多少。
- 哪些站点需要优先关注。

MVP 先输出一个点预测：

```text
预计需求：20 次
```

后期增加概率预测后，可以输出：

```text
预计需求：20 次
可能范围：14 到 29 次
```

预测区间比只给一个数字更有价值，但为了先完成功能，它会放在 TCN 点预测之后实现。

## 4. 系统中的每个部分在做什么

可以用一个物流仓库来理解整个系统。

| 技术 | 通俗解释 | 在项目中的工作 |
|---|---|---|
| 模拟器 | 数据生成员 | 产生测试用的事件数据 |
| Flume | 文件搬运工 | 后期负责把新增文件送到消息队列 |
| Kafka | 传送带 | 暂存和传递大量事件 |
| Spark Streaming | 实时加工线 | 每隔一段时间汇总最新需求 |
| Spark SQL | 离线分析车间 | 制作历史特征和训练数据 |
| MySQL | 仓库 | 保存统计、预测和系统状态 |
| PyTorch | 预测大脑 | 学习历史规律并预测未来 |
| MLflow | 实验记录本 | 后期记录哪个模型效果最好 |
| FastAPI | 服务员 | 把数据整理后交给前端 |
| Vue | 控制面板 | 展示图表和操作页面 |
| ECharts | 图表工具 | 画出趋势、区间和排行榜 |

用户不需要知道传送带和加工线怎么运行。用户只需要打开页面，选择站点，然后看到未来需求。

## 5. 数据是怎样流动的

### 第一步：收集

当前 MVP 使用 Python 虚拟数据生成器制造历史记录和实时事件。生成的数据包含早晚高峰、工作日与周末差异、天气变化和随机异常。

例如：

```text
08:00 到 08:30，站点 A 有 32 次需求
08:00 到 08:30，站点 B 有 7 次需求
```

### 第二步：传输

MVP 由 Python 生成器直接把数据发送到 Kafka。Kafka 像传送带一样，把数据交给后面的计算模块。后期接入文件数据时，再增加 Flume。

### 第三步：实时汇总

Spark Streaming 把事件整理成 30 分钟一组的指标：

```text
站点 A，08:00 到 08:30，需求 32
站点 B，08:00 到 08:30，需求 7
```

### 第四步：制作特征

模型不能直接理解“周一早上 8 点在地铁站”。系统需要把数据变成模型可以使用的数字：

- 上一小时需求是多少。
- 昨天同一时间需求是多少。
- 是否周末。
- 是否节假日。
- 是否下雨。
- 站点容量和邻近站点需求。

### 第五步：训练模型

模型学习类似这样的规律：

```text
如果今天是工作日早上 8 点，
天气晴朗，
过去三天同一时间需求都高，
那么今天早上这个站点也可能出现高需求。
```

这不是简单写死规则，而是模型从大量历史样本中学习规律。

### 第六步：生成预测

模型先输出未来 48 个时间点，每个时间点一个预测值。

后期增加概率预测后，每个时间点再输出三个值：

- q10：较保守预测。
- q50：中位数预测。
- q90：较激进预测。

### 第七步：展示与决策

前端把历史需求与预测画成折线图。运营分析师可以看到：

- 未来哪里需求高。
- 哪个时间点风险最大。
- 哪个模型生成了结果。
- 当前数据是否过期。
- 是否应该优先调度。

## 6. 为什么不能随机划分训练集和测试集

假设模型要预测周五的需求，却提前看到了周六的数据，那么测试成绩会很好，但真实使用时做不到，因为现实中周五永远看不到周六的数据。

这叫数据泄漏。

正确做法是按时间划分：

```text
前面一段时间训练 -> 后面一段时间验证 -> 最后一段时间测试
```

更严格的方法是滚动回测：

```text
用 1 到 20 天预测第 21 天
用 2 到 21 天预测第 22 天
用 3 到 22 天预测第 23 天
```

这样更接近真实工作中的“每天根据昨天以前的数据预测今天”。

## 7. 为什么要做多个模型

只有一个复杂模型，无法证明它真的值得使用。项目至少需要：

| 模型 | 作用 |
|---|---|
| Seasonal Naive | 昨天同一时间是多少，今天也预测多少 |
| Spark MLlib | 用表格特征做快速、可解释的基线 |
| TCN | 用卷积学习时间规律 |
| PatchTST | 后期用 Transformer 学习长期依赖 |

只有最终模型明显优于简单基线，项目才有说服力。

例如不能说“我的模型 MAE 是 4.2”，还必须说明：

```text
Seasonal Naive MAE = 6.1
最佳模型 MAE = 4.2
相对降低 31%
```

所有数字都必须来自真实实验。

## 8. 怎样评价预测效果

### MAE

平均绝对误差。数值越小越好。

```text
如果真实需求是 20，预测是 18，误差就是 2
```

### RMSE

对大误差更敏感。如果偶尔出现严重错误，RMSE 会明显变大。

### sMAPE

用百分比比较误差，适合不同需求规模的站点。

### WQL（后期）

评价预测区间。它不仅关心预测是否接近，还关心 q10 到 q90 是否覆盖真实值，以及区间是否过宽。

### 分组误差

总体平均只能说明一部分问题。我们还要看：

- 早高峰表现。
- 下雨天表现。
- 周末表现。
- 高需求站点表现。
- 第 1 步和第 48 步表现。

## 9. 页面应该展示什么

### 总览页

展示今天的总需求、未来高峰站点、异常站点、数据新鲜度和当前模型版本。

### 预测页

展示某个站点过去 7 天的需求和未来 24 小时预测。概率预测完成后，再增加 q10 到 q90 阴影区间。

### 模型页

展示 Seasonal Naive 和 TCN 的 MAE、RMSE、sMAPE、训练时间和预测状态。

### 数据页

展示数据最新时间、缺失率、迟到数据比例和异常记录。

### 管理页

允许管理员触发预测、查看任务状态和发布新模型。

## 10. 这个项目如何帮助 PS

PS 不要只写：

> 我使用 Kafka、Spark 和 PyTorch 完成了城市需求预测。

更有说服力的写法是：

> 我关注到调度人员能看到当前需求，却无法提前判断未来高峰。由于真实运营数据暂时无法获取，我先设计了包含周期、天气和异常扰动的虚拟数据生成器，再构建城市需求预测系统，将虚拟数据和日历特征整合到实时与离线两条数据链路中。项目最大的挑战不是模型本身，而是保证虚拟数据规律合理、统一事件时间和处理时间，并避免随机切分造成的数据泄漏。最终系统可以输出未来 24 小时预测，并在页面中展示模型误差和站点优先级。

这种写法展示的是问题意识、技术选择和判断过程，而不是技术名词列表。


## 12. 五分钟演示脚本

### 第 1 分钟：问题

“运营人员通常只能看到当前哪里缺车，但调度需要提前发生。我的项目预测未来 24 小时的需求，并给出不确定性范围。”

### 第 2 分钟：数据

“由于真实数据暂时无法获取，我先设计了虚拟数据生成器。数据包含高峰、周末和天气规律，并通过 Kafka 进入 Spark Streaming，离线链路通过 Spark SQL 生成特征。”

### 第 3 分钟：模型

“我先建立 Seasonal Naive 基线，再使用 PyTorch TCN。模型输出未来 48 步预测，通过时间顺序回测和 MAE、RMSE、sMAPE 评估。”

### 第 4 分钟：产品

“页面展示历史需求、未来预测、模型指标和更新状态。运营人员可以按预测缺口查看站点优先级。”

### 第 5 分钟：反思

“项目中最重要的不是堆叠模型，而是避免数据泄漏、保证特征时间一致，并理解哪些场景下模型仍然不可靠。”

## 13. 常见问题

### 这和普通机器学习分类有什么区别？

分类是判断“属于哪一类”，时序预测是预测“未来一段时间会是多少”。它更关心时间顺序、周期、趋势和过去数据。

### 为什么预测未来 24 小时？

24 小时可以覆盖一个完整的调度周期，同时不会因为预测太远导致误差过大。后续可以扩展到 7 天。

### 为什么不只预测一个数字？

一个数字更简单，也更容易先完成 MVP。后期增加 q10 到 q90 区间后，可以帮助运营人员判断是否需要人工复核。

### 为什么不用随机森林或 XGBoost 就够了？

树模型可以成为强基线，但复杂时序关系、长距离依赖和多步预测仍然可能需要深度模型。项目会先证明基线表现，再判断是否值得增加复杂度。

### 为什么 Spark 和 PyTorch 不互相替代？

Spark 擅长处理大量数据和分布式特征，PyTorch 擅长训练深度模型。两者处理的是不同阶段的问题。

### 项目最大的难点是什么？

不是调用模型，而是保证时间口径一致、避免数据泄漏、处理缺失和异常、设计合理回测，并把预测真正转化为行动建议。

## 14. 评审时最值得强调的三点

1. 完整闭环：从数据进入到用户看到预测。
2. 严谨评估：按时间滚动回测，和基线公平比较。
3. 决策价值：不仅输出数字，还输出站点优先级和后续可扩展的风险表达。

## 15. 一句话收尾

UrbanFlow 想做的不是“预测一个数字”，而是把城市未来可能发生的需求变化，提前变成运营人员可以理解和执行的行动依据。
