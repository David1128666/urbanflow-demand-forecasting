### 1.1 核心决策

项目当前采用“MVP 优先、虚拟数据优先、真实数据后置”的策略：

- 先使用 Python 生成带有规律和噪声的虚拟城市需求数据。
- 先跑通 Kafka、Spark、MySQL、模型、FastAPI 和 Vue 的核心链路。
- 第一版只实现 Seasonal Naive 和一个小型 PyTorch TCN。
- Flume、Parquet、MLflow、PatchTST、真实数据、权限和高级监控后置。
- 功能实现优先于数据规模、模型复杂度和生产级架构。

## 2. 项目背景

共享单车、网约车、公共交通和城市配送等场景都存在明显的时空需求波动。运营人员通常知道当前哪里需求高，却很难提前判断未来几个小时的站点需求，因此容易出现以下问题：

- 高峰区域车辆或运力不足，用户等待时间长。
- 低峰区域资源闲置，调度成本高。
- 天气、节假日和大型活动带来的需求突变难以提前响应。
- 传统统计报表只能解释过去，不能支持主动决策。

UrbanFlow 最终会整合真实历史出行、天气和日历数据。当前 MVP 先使用虚拟数据，预测城市站点未来 30 分钟到 24 小时的需求，并将预测转换为简单的站点优先级建议。

## 3. 项目定位

UrbanFlow 不是单纯的“训练一个 LSTM”或“展示一张预测曲线”，而是一个从数据到页面的完整数据产品。MVP 只实现最小闭环，后续再逐步增强：

1. 数据层负责采集、清洗和标准化城市需求数据。
2. 计算层同时支持实时指标和离线特征。
3. 模型层提供基线、机器学习和深度时序模型。
4. 服务层通过 API 提供预测、评估和调度建议。
5. 展示层通过 Vue 和 ECharts 呈现趋势、误差和异常。
6. 工程层先提供可复现环境和核心测试，持续集成后置。

## 4. 核心问题

### 4.1 预测问题

给定某站点或区域截至时间 `T` 的历史需求，以及时间 `T` 已知的天气、日历和空间信息，预测 `T + 30 分钟` 到 `T + 24 小时` 的需求。

```text
输入：过去 7 天到 28 天的需求序列、天气、日历、站点属性和邻近区域信息
输出：未来 48 个 30 分钟时间点的需求点预测
后期输出：10%、50%、90% 分位数和预测区间
```

### 4.2 决策问题

预测本身不是最终目标。系统还需要回答：

- 哪些站点在未来 2 小时可能出现需求缺口？
- 哪些站点适合作为车辆或运力调度的起点？
- 当前哪些站点最可能出现需求缺口？
- 预测结果是否足以支持简单的人工调度判断？

## 5. 项目目标

### 5.1 数据目标

- 使用可配置的虚拟数据生成器模拟历史数据和实时增量。
- 预留真实公开数据适配器，后期可以替换虚拟数据源。
- 建立统一的事件时间、站点编码、时区和聚合口径。
- 提供基础字段校验、随机噪声和异常值。

### 5.2 模型目标

- 建立 Seasonal Naive 基线。
- 建立一个小型 PyTorch TCN，输出未来 48 步点预测。
- 使用时间顺序切分和基础滚动回测，避免数据泄漏。
- 比较模型在高峰、低峰、工作日和周末场景下的表现。
- 概率预测、复杂模型和高级误差解释后置。

### 5.3 工程目标

- 沿用 Kafka、Scala、Spark、MySQL、FastAPI、Vue 和 ECharts。
- 新增 PyTorch 作为深度时序模型框架。
- Flume 和 MLflow 作为后期增强项。
- 提供最小 Docker Compose、环境变量模板和核心测试。
- 所有实验能够通过固定随机种子和配置文件复现。
- 满足 GitHub 开源最低要求：README、LICENSE、.gitignore、贡献指南、安全政策、Issue/PR 模板和 CI。

### 5.4 展示目标

- 展示当前需求、历史趋势和未来预测。
- 展示历史趋势、未来预测和不同模型的误差比较。
- 展示站点排行和简单的调度优先级。
- 展示模型版本、训练时间和数据更新时间。
- 预测区间、区域热力和漂移状态后期再增加。

## 6. 非目标

MVP 阶段不包含以下内容：

- 完整的车辆路径优化和真实运力调度系统。
- 对接真实企业生产数据库或隐私数据。
- 多租户、计费和复杂权限系统。
- 亚秒级实时预测。
- 覆盖全国所有城市和所有出行方式。
- 一开始就训练超大模型或使用昂贵 GPU。
- 用真实业务收益数字替代尚未完成的实验结果。

## 8. 核心使用场景

### 场景 A：查看未来 24 小时需求

1. 运营分析师打开预测看板。
2. 选择一个城市区域或站点。
3. 系统展示历史需求、未来 48 个预测点和预测区间。
4. 系统标记高峰、异常和低置信度时间段。
5. 分析师查看产生高峰的主要原因。

### 场景 B：生成调度优先级

1. 系统计算每个站点未来 1 到 4 小时的需求缺口。
2. 系统结合站点位置、当前库存和邻近站点需求排序。
3. 页面展示高优先级站点和推荐调度方向。
4. 分析师可以将建议导出或人工调整。

### 场景 C：训练和比较模型

1. 数据科学家选择特征版本和时间窗口。
2. 系统执行 Seasonal Naive、Spark MLlib 和 PyTorch 模型。
3. 系统记录参数、指标、图表和模型文件。
4. 系统选择验证集表现最好的模型。
5. 管理员将模型发布为新的预测版本。

### 场景 D：监控数据与模型

1. 系统检查数据最新时间和缺失率。
2. 系统计算最近 7 天的滚动误差。
3. 系统比较训练分布和当前分布。
4. 当误差或漂移超过阈值时，页面显示告警。
5. 管理员决定继续观察、重训或回滚模型。

## 9. MVP 范围

### 9.1 数据

MVP 使用 Python 虚拟数据生成器，默认生成 1 个城市、20 个站点、90 天、30 分钟粒度的数据。数据中应包含早晚高峰、工作日与周末差异、天气扰动、节假日扰动和随机异常。

真实城市数据作为后期适配器实现。后期接入 Chicago Divvy 或其他公开数据时，必须记录来源、许可证和下载时间。

### 9.2 预测粒度

- 时间粒度：30 分钟。
- 预测范围：未来 24 小时。
- 预测步数：48。
- 空间粒度：站点级，后续扩展到区域网格。
- 预测方式：批量生成，每 30 分钟刷新。

### 9.3 模型

MVP 至少包含：

1. Seasonal Naive 基线。
2. PyTorch TCN 深度预测模型。

Spark MLlib、PatchTST、Temporal Fusion Transformer、图神经网络和多模态事件特征放入后续阶段。

### 9.4 页面

1. 总览看板。
2. 区域与站点预测页。
3. 模型评估页。

数据质量、告警和管理页后续增加。

## 11. 非功能需求

### 11.1 性能

- 实时数据从 Kafka 到 MySQL 的延迟目标：小于 60 秒。
- 普通查询 API 的 P95：小于 300 毫秒。
- 批量预测 20 个站点未来 48 步：小于 1 分钟。
- 前端首屏加载：本地演示环境小于 3 秒。

### 11.2 可靠性

- Kafka 消费支持 checkpoint 和重复消息幂等处理。
- 模型训练失败不能覆盖上一个可用模型。
- 预测服务不可用时，API 返回最近一次有效预测和状态提示。
- 所有任务记录开始时间、结束时间、状态和错误信息。

### 11.3 可复现性

- 固定依赖版本和随机种子。
- 数据和模型使用版本号。
- 训练命令写入 README。
- 测试数据与真实数据分开保存。
- 不提交密钥、密码和大型模型文件。

### 11.4 安全性

MVP 可以先不实现登录。后续增加认证时：

- 密码使用 bcrypt 或 Argon2，不使用静态 SHA256 盐值。
- JWT 使用成熟库，不使用手写实现。
- 生产环境限制 CORS 来源。
- 数据库连接信息通过环境变量注入。
- API 不向客户端返回完整内部异常。

### 11.5 可维护性

- 后端按 Router、Service、Repository 分层。
- 预测引擎按数据、特征、模型、评估、推理分层。
- 数据库变更使用版本化 SQL 或迁移工具。
- 关键业务逻辑包含单元测试。

## 13. 成功指标

### 13.1 模型指标

- MAE：预测值与真实值的平均绝对误差。
- RMSE：对大误差更敏感，用于检查异常预测。
- sMAPE：用于比较不同需求规模的站点。
- 相对 Seasonal Naive 的 MAE 改善比例。
- 高峰、雨天、节假日等关键场景的单独表现。

WQL 和预测区间覆盖率属于后续概率预测阶段。

### 13.2 工程指标

- 数据新鲜度。
- 任务成功率。
- API 可用率和响应时间。
- 单元测试覆盖率。
- 从干净环境启动项目的成功率。

### 13.3 展示指标

- 用户能否在 30 秒内找到未来高峰站点。
- 用户能否理解预测区间代表的风险。
- 用户能否根据页面完成一次调度优先级判断。
- 评审人能否仅通过 README、架构图和演示理解项目。

## 14. 验收标准

项目满足以下条件时，认为 MVP 完成：

1. 新环境可以按照 README 完成安装和启动。
2. 虚拟数据可以通过 Kafka 进入实时链路。
3. Spark 能生成实时指标和离线特征。
4. Seasonal Naive 和 TCN 能够在相同回测协议下比较。
5. 最佳模型相对 Seasonal Naive 有可解释的提升。
6. 预测结果可以通过 FastAPI 查询。
7. Vue 页面可以展示预测、误差和模型状态。
8. 数据库、模型和 API 有基础测试。
9. 文档明确说明当前使用虚拟数据。
10. 文档包含架构图、设计说明和演示脚本。
11. 仓库包含 MIT License、贡献指南、安全政策和 Issue/PR 模板。
12. `.gitignore` 和 `.env.example` 可以防止密钥与生成数据进入 Git。
13. GitHub Actions 至少可以执行一条有效的质量检查。

## 15. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 真实数据暂时获取困难 | 无法开始建模 | 先使用虚拟数据跑通完整功能 |
| 虚拟数据过于随机 | 模型学不到规律 | 加入周期、趋势、天气和异常规则 |
| 时间切分不正确 | 模型指标虚高 | 禁止随机切分，统一滚动回测 |
| 需求数据稀疏 | 模型难以学习 | 使用区域聚合、零膨胀处理和分层预测 |
| 天气数据缺失 | 特征不完整 | 保留缺失指示变量，使用最近邻时间填充 |
| 深度模型收益不稳定 | 项目周期延误 | 先完成基线，再逐层增加复杂度 |
| GPU 资源不足 | 训练周期长 | MVP 使用小型 TCN，CPU 也可运行 |
| 前端先于数据完成 | 只能展示假数据 | 优先打通数据和模型最小闭环 |
| 文档与代码不一致 | 影响开源可信度 | 将文档更新列入 Definition of Done |

## 16. 实施计划

采用 Agent 连续开发后，首个可运行版本压缩为 7 天：

| 天数 | 目标 | 主要产出 |
|---|---|---|
| 第 1 天 | 骨架与基础设施 | Maven、Python、Vue、Docker、数据库表 |
| 第 2 天 | 虚拟数据与 Kafka | 数据生成器和实时事件 |
| 第 3 天 | Spark 实时链路 | MySQL 中的 30 分钟需求指标 |
| 第 4 天 | 特征与基线 | 时间特征和 Seasonal Naive 指标 |
| 第 5 天 | TCN 与服务 | 48 步预测、FastAPI 查询 |
| 第 6 天 | 页面与发布准备 | Vue 页面、测试、README、Release |
| 第 7 天 | GitHub 上传 | 首版代码、标签和已知问题 |

该计划重点是完成基础可运行版本和首次上传。高级模型、真实数据和复杂监控继续在后续版本迭代。

## 18. 项目叙事

CV 中应突出完整链路和可量化成果：

> 构建城市需求时序预测平台，设计可配置的虚拟数据生成器，完成 Kafka、Spark Streaming、Spark SQL、MySQL、PyTorch、FastAPI 和 Vue 的端到端实现；建立 Seasonal Naive 与 TCN 模型，并通过时间顺序回测比较不同模型在高峰和工作日场景下的表现。

PS 中应突出问题和思考：

> 我关注到城市运营系统通常只能描述已经发生的需求，而调度决策发生在需求到来之前。由于真实运营数据暂时无法获取，我先设计了包含周期、天气和异常扰动的虚拟数据生成器，用最小可行系统验证完整预测流程。项目过程中最大的挑战不是模型本身，而是如何保证数据生成规律合理、避免时间数据泄漏，并让预测结果最终可以在页面中理解和展示。

具体提升比例和误差数字必须来自实际实验，不应提前编造。
