# 第 12.5 步验收报告：业务语义与调度闭环

> **English summary:** This report verifies inventory, shortage calculation,
> dispatch work orders, simulated impact, API fields, UI behavior, and the
> limitations of synthetic-data results.
>
> **中文摘要：** 本报告验收库存、缺口计算、调运工单、模拟影响、API 字段、
> 页面行为，并明确虚拟数据结果的边界。

> GitHub 展示版本默认使用英文。中文界面、API 文案和调度文案已经分别保存在
> 前端 `zh-CN.js`、后端 `zh_CN.py` 和数据侧本地化资源中。

## 1. 本次增强解决了什么问题

基础版只能回答“未来每个 30 分钟有多少订单”，但运营人员还需要回答：

1. 这个数字到底代表什么。
2. 哪个站点会在什么时间缺车。
3. 现在缺多少辆，建议补多少辆。
4. 车辆应该从哪里调来。
5. 最晚什么时候执行。
6. 执行后预计改善多少。

本次增强把“预测曲线”扩展为“预测 -> 缺口 -> 调度工单 -> 模拟影响”的决策闭环。

## 2. 统一业务口径

| 字段 | 业务含义 | 注意事项 |
|---|---|---|
| 骑行订单 | 指定 30 分钟窗口内预计发生的骑行订单数 | 不是人数、收入或车辆故障数 |
| 当前可借车辆 | 最新库存快照中用户可以扫码借走的车辆数 | 不代表未来仍保持该数量 |
| 未来 2 小时订单 | 未来 4 个 30 分钟窗口的预测订单累计 | 本次调度使用的需求窗口 |
| 安全库存 | 为订单波动额外保留的车辆 | 当前默认至少 2 辆，并取 2 小时订单的 10% |
| 目标备车 | 未来 2 小时订单取整后加安全库存 | 站点执行调度前应达到的车辆目标 |
| 车辆缺口 | 目标备车减当前可借车辆，最低为 0 | 表示需要补充的车辆数 |
| 调运工单 | 从盈余站点向缺车站点调运指定数量车辆 | 包含距离、优先级和执行截止时间 |
| 模拟改善 | 假设工单按时执行后，已识别缺口减少的比例 | 不是真实收益，也不是已执行结果 |

## 4. API 增强

### 4.1 预测接口

接口：

```text
GET /api/v1/forecasts/latest?station_id=ST019&limit=48
```

新增 `operation_summary`，包含：

- 未来 2 小时订单。
- 未来 24 小时订单。
- 当前可借车辆和空桩。
- 安全库存。
- 目标备车。
- 建议补车数量。
- 运营状态。
- 可直接显示的中文建议动作。
- 预测窗口起止时间。

### 4.2 调度接口

接口：

```text
GET /api/v1/dispatch/summary
GET /api/v1/dispatch/recommendations
```

新增或增强字段：

- 站点中文名称。
- 优先级等级。
- 状态标签。
- 调运动作全文。
- 目标备车数量。
- 缺口减少数量。
- 缺口减少比例。
- 工单提前量。
- 风险订单覆盖比例。
- 数据模拟说明。

## 7. 已知限制

1. 当前全部数据为虚拟演示数据，站点名称也是明确的演示名称。
2. 2 小时订单累计没有模拟车辆归还后的再次使用，因此缺口计算偏保守。
3. 用户发现无车后可能改用其他站点，所以“风险订单”不能直接等同真实流失订单。
4. 100% 表示已识别缺口全部被建议工单覆盖，不代表真实运营改善一定达到 100%。
5. 当前没有真实调度员确认、工单执行回写和车辆实时 GPS。
6. 当前没有计算人工、车辆运输和调度成本，因此不展示货币收益。

## 8. 后续增强方向

1. 接入真实车辆库存和骑行订单数据。
2. 加入车辆归还预测，计算净需求而不是单向借车需求。
3. 增加调度员接单、执行、完成和失败回写。
4. 加入车辆运输载具容量和多站合并路线。
5. 增加服务损失、调度成本和碳排放的模拟评估。
6. 对预测误差进行区间估计，避免只展示单点预测。
