# UrbanFlow 代码制作任务计划

> **English summary:** This document records the implementation order,
> completion criteria, verification results, and next steps for the UrbanFlow
> codebase. Detailed sections are preserved in Chinese.

这份计划用最直白的方式说明：代码要从哪里开始、每一步做什么、做到什么程度才算完成。

核心原则只有四句话：

1. 一次只完成一个阶段，不要同时开工很多模块。
2. 每一步完成后都必须能运行、能检查、能提交 Git。
3. 先使用虚拟数据，不依赖暂时拿不到的真实城市数据。
4. 先完成可用功能，再优化模型效果和工程规模。

因为采用 Agent 连续开发，本周目标是：

```text
第 1 天完成骨架
第 2 到第 5 天逐条完成数据、实时链路、模型和页面
第 6 天完成测试、文档和 GitHub 发布准备
第 7 天上传首版并记录问题
```

这里的“一周”目标是完成基础可运行版本和首次上传，不等于一周内完成所有高级功能。

## 一、最终要完成什么

MVP 最终只完成下面这条链路：

```text
Python 生成虚拟数据
  -> Kafka 接收数据
  -> Spark 实时汇总
  -> MySQL 保存结果
  -> Spark SQL 制作特征
  -> Seasonal Naive + PyTorch TCN 预测未来 48 个时间点
  -> FastAPI 提供查询接口
  -> Vue + ECharts 展示需求、缺口和调运工单
  -> MySQL 产生可执行的数据结果
```

第一版暂时不做：

- 真实城市数据
- Flume
- MLflow
- PatchTST 和大型模型
- 概率预测区间
- 登录权限
- 高级调度优化、真实 GPS 调度和车辆归还预测
- Kubernetes 和云部署

## 二、代码文件夹计划

后面的代码最终放在 `code/` 下面，建议按下面的方式拆分：

```text
code/
├── common/                  # Scala 公共配置、数据模型和工具
├── realtime-analysis/       # Spark Structured Streaming 实时计算
├── offline-analysis/        # Spark SQL 离线特征和统计
├── forecast-engine/         # Python 数据、模型、训练、评估和预测
├── backend/                 # FastAPI 后端
├── frontend/                # Vue 3 页面
├── simulator/               # Python 虚拟数据生成器
├── sql/                     # MySQL 建表脚本
├── docker/                  # Kafka、MySQL 等本地环境
└── tests/                   # 跨模块测试
```

真正的数据、模型文件和运行日志不会上传到 Git。

## 四、一周压缩节奏

| 天数 | 主要任务 | 当天应完成的结果 |
|---|---|---|
| 第 1 天 | 项目骨架、前后端最小工程、Docker、数据库表 | 所有模块可以独立启动，基础 CI 可运行 |
| 第 2 天 | 虚拟数据和 Kafka | 一条命令生成数据，事件可以进入 Kafka |
| 第 3 天 | Spark 实时聚合并写入 MySQL | Kafka 数据可以变成 30 分钟指标 |

## 六、开发时不要做的事

- [ ] 不要为了展示技术而加入无关组件。
